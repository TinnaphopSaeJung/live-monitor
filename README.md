# Live Monitor

Live Monitor is an internal monitoring system for live-streaming machines that use OBS Studio.

Its main goal is to detect audio problems during a live session as early as possible and notify the team through LINE before the issue goes unnoticed for too long.

> Live Monitor currently observes the OBS side of the audio pipeline. It can detect problems around OBS and the monitoring agent, but it cannot guarantee that viewers on the streaming platform are actually receiving audio. Viewer-side / end-to-end monitoring is planned for a later phase.

---

## Features

- Monitor audio from a specific OBS input
- Detect common audio failures
  - microphone muted
  - audio signal lost
  - audio level abnormally low
  - OBS audio samples stopped arriving
  - invalid audio track routing
- Monitor whether the local Agent is still reachable
- Send heartbeat status from each streaming machine to the backend
- Store machine state, incidents, and incident events in PostgreSQL
- Send incident alerts and recovery notifications to a LINE group
- Resolve open audio incidents automatically when streaming stops
- Support multiple streaming machines

## Audio Detectors

### `AUDIO_MUTED`

Triggered when OBS reports that the monitored input is muted.

```text
muted=true
↓
AUDIO_MUTED
```

---

### `SIGNAL_LOST`

Triggered when audio samples are still being received, but there is no audio signal for the configured duration.

```text
audio samples still arriving
+
signal=false
+
not muted
+
continuous for signal_loss_duration
↓
SIGNAL_LOST
```

This is different from low volume and different from missing samples.

---

### `AUDIO_TOO_LOW`

Triggered when the audio level remains below the configured threshold for long enough.

The detector aggregates raw OBS meter events into short windows and evaluates the maximum level in each window. This helps avoid false positives caused by very short silent gaps between speech.

```text
level <= low_level_threshold_db
for low_level_duration
↓
AUDIO_TOO_LOW
```

---

### `AUDIO_SAMPLE_STALLED`

Triggered when the Agent stops receiving audio samples for the monitored OBS input while monitoring is active.

```text
no audio.Sample received
for sample_stall_duration
↓
AUDIO_SAMPLE_STALLED
```

This detector helps identify cases such as:

- monitored input renamed or removed
- OBS meter events stop arriving
- `InputVolumeMeters` subscription is unavailable
- partial OBS / event pipeline failure

---

### `ROUTING_INVALID`

Checks whether the monitored OBS input is assigned to the audio track used by the live stream.

---

### `AGENT_UNREACHABLE`

This incident is generated by the backend rather than by the Agent.

When the last known state says that monitoring is active, but heartbeats stop arriving for longer than the configured threshold, the backend opens:

```text
AGENT_UNREACHABLE
```

Possible causes include:

- Agent process stopped
- machine went to sleep / hibernate
- machine powered off
- network disconnected
- operating system became unresponsive

---

## Monitoring Context

Audio incidents are relevant only while the stream is actively being monitored.

Typical stream lifecycle:

```text
STOPPED
monitoring=false

STARTING
monitoring=false

STREAMING
monitoring=true

STOPPING
monitoring=false

STOPPED
monitoring=false
```

When streaming stops, active audio incidents are closed with:

```text
MONITORING_STOPPED
```

This is intentionally different from a normal recovery.

## Agent Configuration

Example:

```yaml
agent:
  machine_id: "LIVE-PC-01"
  heartbeat_interval: "5s"

backend:
  enabled: true
  base_url: "https://your-backend.example.com"
  agent_token: "YOUR_AGENT_TOKEN"
  request_timeout: "5s"

obs:
  host: "127.0.0.1"
  port: 4455
  password: "YOUR_OBS_WEBSOCKET_PASSWORD"
  audio_input: "Mic/Aux"

audio:
  signal_loss_duration: "10s"

  low_level_threshold_db: -90
  low_level_duration: "10s"
  low_level_window_duration: "1s"

  recovery_duration: "5s"

  sample_stall_duration: "5s"
  sample_recovery_duration: "5s"
```

### Important per-machine values

These values normally need to be checked for every machine:

```yaml
agent:
  machine_id: "UNIQUE_MACHINE_ID"

obs:
  password: "OBS_WEBSOCKET_PASSWORD"
  audio_input: "EXACT_OBS_INPUT_NAME"
```

`machine_id` must be unique.

`audio_input` must exactly match the input name in OBS.

`127.0.0.1` should normally remain unchanged because the Agent and OBS run on the same machine.

## HTTP Endpoints

### Agent Heartbeat

```http
POST /api/v1/agents/heartbeat
Authorization: Bearer <AGENT_TOKEN>
```

Updates the current machine state.

---

### Incident Event

```http
POST /api/v1/incidents/events
Authorization: Bearer <AGENT_TOKEN>
```

Persists incident open / resolved events.

LINE notification delivery is asynchronous and does not block this request.

---

### LINE Webhook

```http
POST /webhooks/line
```

Used for LINE webhook events.

The endpoint validates `X-Line-Signature` using `LINE_CHANNEL_SECRET`.

The webhook was also used to obtain the LINE group ID used for notification delivery.

---

### Health Check

```http
GET /healthz
```

Response:

```text
ok
```

This endpoint is used by the hosting platform for service health checks.

## Recommended Start Flow

Normal operating procedure:

```text
1. Open OBS
2. Start Live Monitor Agent
3. Confirm that the Agent connects to OBS
4. Confirm that heartbeat reaches the backend
5. Start Streaming
```

Why this order?

The monitoring system should already be ready before the live session starts. Starting the stream first creates a period where the live session is running without monitoring.

If the Agent crashes during an active live session, restart the Agent immediately. There is no need to stop the stream first.

---

## Recommended Shutdown Flow

```text
1. Stop Streaming
2. Wait for the backend to receive monitoring=false
3. Preferably wait for:

   stream=STOPPED
   monitoring=false

4. Stop the Agent
```

The important part is that the backend receives `monitoring=false` before the Agent disappears.

Otherwise the backend may still remember:

```text
stream=STREAMING
monitoring=true
```

If heartbeats then stop, the backend correctly assumes that an Agent disappeared during an active live session and opens `AGENT_UNREACHABLE`.

## Incident Lifecycle

Example:

```text
Audio problem detected
        ↓
Incident OPENED
        ↓
Agent sends event to Backend
        ↓
PostgreSQL
        ↓
Notification Worker
        ↓
LINE Alert
```

When the problem recovers:

```text
Detector recovers
        ↓
Incident RESOLVED
        ↓
PostgreSQL
        ↓
Notification Worker
        ↓
LINE Recovered notification
```

Examples of resolution reasons:

```text
RECOVERED
SAMPLES_RESUMED
HEARTBEAT_RESUMED
MONITORING_STOPPED
```

## Database Overview

### `machines`

Stores the latest known state of each monitoring machine.

Examples:

- last heartbeat time
- OBS connection state
- stream state
- monitoring state
- signal state
- level state
- mute state
- routing state
- sample state

---

### `incidents`

Stores the current / summarized lifecycle of each incident.

Example:

```text
AUDIO_MUTED
OPENED → RESOLVED
```

---

### `incident_events`

Stores immutable incident events.

Example:

```text
OPENED
RESOLVED
```

The relationship between `incidents` and `incident_events` is currently logical rather than a direct `incident_id` foreign key. Events are correlated through fields such as machine, incident type, and incident start time.

## Security Notes

Current protections include:

- HTTPS between Agent and backend
- bearer token authentication for Agent endpoints
- LINE webhook signature validation
- PostgreSQL is accessed only by the backend
- Agents do not connect directly to the database
- request body limit on the LINE webhook

Important future hardening work:

- API rate limiting
- request body limits on Agent endpoints
- per-machine Agent tokens
- binary code signing for Windows and macOS
- stronger release / binary verification

Never commit:

- Agent token
- OBS websocket password
- LINE Channel Access Token
- LINE Channel Secret
- database credentials

## Current Limitations / Known Blind Spots

The current pilot intentionally leaves several items for later improvement.

### Runtime Stream Track Change

The Agent checks stream track configuration, but changing the OBS Advanced stream track while the Agent is already running is not fully handled yet.

### OBS Reconnect State

More complete runtime handling for OBS websocket disconnect / reconnect and accurate `obs_connected` state is still planned.

### Multi-PC End-to-End Testing

The system is currently being piloted across multiple machines, but broader end-to-end testing is still ongoing.

### Viewer-Side Monitoring

The current system observes OBS, not the final viewer playback on Shopee or other streaming platforms.

A healthy OBS-side state does not guarantee that viewers can hear the stream.

## Project Scope

Live Monitor is currently an internal operational tool.

The focus is reliability and early detection of live-streaming problems rather than acting as a full observability platform.

The system is intentionally being expanded incrementally based on real incidents and pilot feedback.
